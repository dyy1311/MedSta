## 产品概述

把 `docs/timeline.md` 从「混序的 spec 流水账」重建为「倒序的决策时间线」，并据此整理下一步开发计划。文档要能回答三个问题：项目在什么时候、因为什么、改变了什么结构或策略。

## 核心功能

- **统一格式**：四列 `日期 ｜ 类型 ｜ 内容 ｜ 原因/依据`，类型严格限定为 `迁移 / 环境 / 规范 / 结构 / 选型 / 需求` 六类，不新增。
- **严格倒序**：最新日期在最上；同日按「需求 → 结构 → 规范 → 选型 → 环境 → 迁移」排列，规则写在文档头部。
- **覆盖全部开发痕迹**：001–025 每个 spec 的落地、每次目录重组、每条技术选型结论、每次规范变更、每次 spec 阶段回退，都能在表里找到一行；007 因无独立 spec 文档，保留事件并注明。
- **决策与流水分离**：spec 完成记「做了什么」，决策记「为什么这么定」，两者都进时间线但类型不同，避免把决策埋在一长串说明文字里。
- **维护规则内化**：文档头部写明「什么情况必须留一条」，后续任何人（含 AI）改架构前先读这里。

## 视觉与结构

单一 Markdown 文档，按日期分节（`### 2026-10-23`）+ 每节内四列表格；顶部是用途、维护规则、类型定义三块；不引入第二个决策文件，避免双份真相源。

## 下一步计划

在 `TO_DO.md` 重构 roadmap：P0 保留三项（生存分析族、缺失数据路径、Estimand/SAP），按「依赖关系 + 用户可见价值 + 成本」给出推荐顺序与验收口径；P1 精选会话持久化、数据清洗、上传限额；P2 保持工程项。

## 技术方案

### 文件与结构

仅改文档，不动代码：

```

TO_DO.md                  # [MODIFY] roadmap 重排 + 已完成表去重
CODEBUDDY.md              # [MODIFY] 开发流程中 timeline 的格式约定
spec/README.md            # [MODIFY] 流转规则中「时间线记录」的格式引用
```

`docs/timeline.md` 结构：

```markdown
# MedSta 开发时间线

> 用途 / 与 spec、TO_DO、design-notes 的分工

## 维护规则
- 必须留条目的六种情形（目录重组、依赖变更、规范变更、选型定稿、需求增删、spec 回退）
- 不必留条目的情形（纯 bug 修复且无契约变化、文案调整）

## 类型定义
| 类型 | 判定标准 | 示例 |

## 时间线
### 2026-10-23
| 日期 | 类型 | 内容 | 原因/依据 |
...
### 2026-10-21
...
```

### 条目重建方法

历史无法从 git 恢复（仅 2 次提交），因此以四类素材交叉重建，逐条归类：

| 素材 | 提取内容 |
| --- | --- |
| 现有 `docs/timeline.md` 34 行 | 事件主干与日期 |
| `docs/design-notes.md` 13 节 | 决策依据（Owner 划分、ToolSpec 单一真相源、教材取舍、外部标准引入） |
| `spec/done/*.md`（25 个） | spec 完成事件与产出边界 |
| `docs/evaluation-report.md`、`TO_DO.md` | 缺陷、验收门槛、优先级变化 |


原则：只记录**实际发生**的事，不把计划写成历史；同一事件若既有 spec 完成又有决策，拆成两行（类型不同），不合并成一句长文。

### 条目粒度与写法

- 一行一件事，内容列必须可核对：含文件路径、模块名、阈值、版本号、测试数。
- 原因列优先引用：教材章节号、评估报告门禁（G0–G7）、真实数据实测值、被修复的具体缺陷。
- 禁止「优化了性能」「完善了体验」这类无法验证的表述。
- 预期条目数约 40–45 条：10-23 约 18 条、10-21 约 6 条、10-19 约 4 条、10-18 约 4 条、10-17 约 8 条。

### 与既有文档的分工

| 文档 | 回答的问题 |
| --- | --- |
| `docs/timeline.md` | 什么时候、因为什么、改变了什么（决策与结构） |
| `spec/done/*.md` | 某个功能做什么、行为列表、验收标准 |
| `TO_DO.md` | 接下来做什么、优先级、已知限制 |
| `docs/design-notes.md` | 某个技术决策的完整推理 |


### 验证方式

`docs/timeline.md` 写完后用脚本自检四项，任一失败即返工：

1. 日期严格非递增（`YYYY-MM-DD` 可字符串比较）。
2. 类型列取值 ⊆ 六类集合。
3. 内容列覆盖 001–025 全部编号（007 允许以「无独立文档」注明）。
4. 无重复条目（同日期同类型同内容主体不重复）。

## 实施注意

- **不改代码、不跑测试**：本次是文档重构，验证靠结构自检而非 pytest。
- **保留信息密度**：旧表每条动辄 200 字，重写时不要为了整齐而删掉阈值与测试数，这些是后续复盘依据。
- **007 的边界**：`spec/done/` 无 007 文件，但前端 SPA 确实交付过，条目里注明「spec 文档未单独留存」，不伪造文件路径。
- **旧表第 26 行「待办」**：它不是事件，删除；对应内容已在 `TO_DO.md` 的已知限制里。
- **下一步计划的位置**：`timeline.md` 只记已发生的事，计划写进 `TO_DO.md`，回答里给推荐顺序与理由，避免时间线里混入未来事项。
